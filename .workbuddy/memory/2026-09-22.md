### 1. 列排序：口径收进 `src/utils/tableSort.ts`
- 用 EP 自带 `sortable` + `:sort-method`（**不是 `sortable="custom"`**）：EP 内部对 `:data` 副本排序，
  轮询换数组后仍保持当前排序（实测 9 秒两轮轮询顺序不变），且与筛选 chip 叠加正常。
  代价是排序状态不进 URL —— 换来的是表头箭头状态永远和数据一致，不需要 `default-sort` 回填。
- 三条口径写死在比较器里，视图不许自己写 `a.x > b.x`：
  - 中文 `localeCompare(…, "zh-Hans-CN", { numeric: true })`（码点序会把「批次」排到「报警」后面）；
  - 枚举走 `labels.ts` 新增的次序数组（`batchStatusOrder` / `alarmSeverityOrder` / `recipeStatusOrder` /
    `lotStatusOrder` / `lotSourceOrder` / `occupancyOrder` / `userRoleOrder`），不是拼音也不是字母；
  - **空值垫底只对升序成立**：EP 的降序是把升序比较结果**整体取反**（实测：报警「确认」列升序时未确认在最后，
    降序时未确认翻到最前），不是交换实参。两参数比较器拿不到方向，做不到两个方向都垫底；
    对「确认时间/数量」这类列，降序把空值顶上来恰好是要看的东西，接受并写进注释。
- `DESC_FIRST` 只给时间与数量列（首点=最新/最大在前，第三次点击回到后端默认序）。
  **枚举列不要用它**：次序数组本身就是「该先看谁」的顺序，走默认升序；
  给 `alarmSeverityOrder`（Critical 开头）套 DESC_FIRST 会把首点变成 Info 在前——改的时候踩过一次。
- 覆盖：批次(6 列) / 配方(5) / 报警(6) / 物料批(6) / 设备(8) / 用户(4)。
  **审计页故意不做列排序**：它是 `skip/take` 服务端分页，客户端排只能排本页 50 条，会给出错误结论，

## 全仓设计复评 + 按建议顺序修完 5 项（同日第三批）

用户先问「有哪些设计不合理的地方」，派三路只读走查（执行域 / 基础设施与 API / 前端架构），
**每条结论我都亲自核过 file:line 才写进报告**；随后用户说「按建议顺序开干」= P0-1 → P0-2+P0-3 → P1-8+P1-9。

### P0-1 批次终态不可被引擎覆盖
- 根因：`Fault()` / `Complete()`（`ProductionBatch.cs:137-153`）是**唯一两个没有前置守卫**的迁移方法，
  而 `MarkFaultAsync`（`BatchSchedulerHostedService.cs:353-362`）也不查终态 → 操作员刚中止，
  引擎同 tick 抛异常就把批次改回 Faulted 并覆盖 `FaultMessage` / `CompletedAt`。
  对比 `FlushAsync`（`Waves.cs:967`）是查了 `IsTerminal` 的——同一个不变式只在一半路径上成立。
- 做法：终态判据收进域层 `ProductionBatch.IsTerminalState(status)` + `IsTerminal` 属性，
  `Fault/Complete` 加守卫抛 `ALREADY_DONE`，`Abort` 原来自己写了一份名单也改用它；
  调度器里 `Waves.cs` 的私有 `IsTerminal(BatchStatus)` 变成委托，`MarkAbortedAsync` 的手写状态判断同样换掉。
  `MarkFaultAsync` 撞终态时**只打日志不写库**（不新增报警行：中止与故障同 tick 撞车是竞态常态，
  往 QA 要审的报警清单里塞噪声比让它静默更糟）。
- 测试：`ProductionBatchLifecycleTests` 补 3 条（中止后不可 Fault / 放行后不可 Complete+Fault / Faulted 不算终态可重排）。

### P0-2 停用与改角色即时生效
- 根因：角色取自 JWT claim（`ServiceCollectionExtensions.cs:111`），令牌默认 12 小时；
  `EsignGuard.RequireAsync` 把 signer 查出来了却只验密码不验 `IsActive`——**停用后密码依然是对的**，
  所以"验过密码"不等于"这人还有资格签"。
- 做法：新增 `Api/CurrentUserMiddleware.cs`，在 `UseAuthentication` 之后按主键读一次 users 表：
  停用/已删 → 401 `{code:"SESSION_INVALID"}`（选 401 而非 403 是为了让前端既有的会话过期处理清令牌回登录页，
  停在页内报"角色无权"会让人以为是自己权限配错）；角色与显示名以库为准重写回 ClaimsPrincipal。
  `EsignGuard` 再补一道 `IsActive`。已建立的 SignalR 连接不受影响（注释里写明了边界）。
- **我自己在这一步引入过一个回归**：重建 `ClaimsIdentity` 时把 `nameType` 传成 `ClaimTypes.NameIdentifier`，
  于是 `Identity.Name` 变成用户 GUID，`/api/auth/me` 与审计 actor 都被写成 GUID。
  已改为沿用来源身份的 `identity.NameClaimType / RoleClaimType`，并把这些类型连同 `ClaimTypes.Name/Role` 一起
  从复制循环里排除后重新添加。**教训：改 ClaimsPrincipal 不要新建 identity 传死字面量。**
  开发库里 01:18 那 4 行 `user.update` 审计的 actor 仍是 GUID（是修复前那次探针产生的真实事件，
  按本项目"审计只追加"的规矩没有去改）。

### P0-3 种子口令按账号独立
- 根因：`ResolveInitialPasswords` 里 `Enumerable.Repeat(options.InitialPassword, 5)` —— 五个账号同一口令。
  本系统的电子签名就是"再输一次登录密码"，三审链（工程师提交 → 主管 → 质量）的"不同的人"退化成一份口令。
- 做法：Demo 分支保持五个公开的演示口令不变（**e2e helpers 与 README 依赖它们，别动**）；
  非 Demo 时 `Seed:AdminPassword` 只给 admin，其余四个各自 `GeneratePassword()` 并逐条 LogWarning 一次。
  Demo 且又配了口令时打 warn 说明"配置被忽略"，不静默。
- 测试：新增 `SeedPasswordIsolationTests`（2 条）。**bcrypt 每次加盐，同口令哈希也不同**，
  所以断言必须用 `hasher.Verify(...)` 判"谁能用这个口令登录"，比哈希会假通过。

### P1-8 异常 → HTTP 语义映射收口
- `ExceptionHandlingMiddleware` 原来只映 AUTH/FORBIDDEN/NOT_FOUND，其余全 400。
  现在：`EQ_BUSY` → **423 Locked**（RFC 4918，语义正是"资源被锁"），
  `CONFLICT/DUP_*/ALREADY_DONE/ALREADY_DECIDED/DRAFT_EXISTS/VERSION_MISMATCH` → **409**（一组闭集名单，不是逐个 switch），
  其余仍 400。新增两个 catch：`DbUpdateConcurrencyException` → 409；
  `DbUpdateException` 且内部消息含 "UNIQUE constraint failed" → 409（**其余 DbUpdateException 仍算 500**，
  NOT NULL / FK 违约是程序 bug，不该伪装成冲突）。
- 这条的价值在前端看不见（现在只弹 message），在于"重试可能成功"与"重试一万次也一样错"终于可分流。

### P1-9 追溯读取依赖的唯一索引
- 先核实现状：批次号/物料批/配方编码/设备码/用户名/样品码**本来就有唯一索引**，
  所以那部分真正缺的是上面的 DbUpdateException 映射（P1-8 已补），不是再加索引。
- 真缺的是两条：`recipe_steps(RecipeVersionId, Code)` 与 `approval_records(RecipeVersionId, Level)`。
  理由不是"看着不规范"，而是下游 `BatchService.cs:458` 用 `ToDictionary(s => s.Code)`、
  `RecipeService.cs:151` 用 `Single(Pending)` —— 一条脏数据会让该配方**所有**批次详情与 eBR 永久 500。
- 加索引前先查了开发库：57 工步 / 43 审核记录，重复 0，多 pending 0；并确认
  `Submit()` 与 `ReopenRejected()` 都先 `Approvals.Clear()`，所以 (version, level) 唯一是既有语义。
- 域层同时补 `DUP_STEP_CODE`（`RecipeTopology.Validate` 原来不查重码），给人话错误、DB 索引兜底。

### ⚠️ 这轮最贵的一条经验：EF 外键索引约定会连带改模型
加 `HasIndex(RecipeVersionId, Code)` 之后，EF 的 FK 索引约定发现最左前缀已覆盖外键列，
**就从模型里移除了自动生成的单列 `IX_recipe_steps_RecipeVersionId`**。快照若还留着它 →
`PendingModelChangesWarning`，一次性挂掉 20 多个集成测试（实测就是这么炸的）。
正确做法：快照删掉单列 HasIndex、迁移里真的 `DropIndex` 两条单列索引再建复合索引。
这条也解释了为什么本项目"改迁移必须同步 AppDbContextModelSnapshot.cs"是硬约束。

## 第八轮：审计履历改为服务端排序 + 分页（顺手解开 SQLite 的 DateTimeOffset 限制）

**根因**：`AuditService.QueryAsync` 原先把**整张** `audit_logs` 读进内存再 `OrderByDescending(At)` + 内存 Skip/Take。
原因不是懒，而是 SQLite 提供器对 ORDER BY 原生 `DateTimeOffset` 列直接抛 `NotSupportedException`，
代码注释里写着"真正的解法是给 At 配一个可排序的持久化列"。

**解法（不需要新列、不需要迁移、不需要回填）**：`Infrastructure/Persistence/AuditTimestamp.cs` 给 `At` 挂一个
`ValueConverter<DateTimeOffset, string>`，格式 `yyyy-MM-dd HH:mm:ss.FFFFFFFzzz`、写入前 `ToUniversalTime()`。三点依据：
1. 与 EF 自带 SQLite 映射**逐字符相同**，所以历史行（开发库实测 163 行，偏移全是 `+00:00`）不用动，模型差异也不产生表结构 diff → 无迁移、无 `PendingModelChangesWarning`（启动日志 0 警告已验证）；
2. 提供器的 ORDER BY 禁令是针对它自己的 DateTimeOffset 映射，挂上转换器后这一列在 SQL 眼里是 TEXT，`ORDER BY`/`>=`/分页全部下推；
3. 这个写法的日期时间部分定宽、小数秒变短不会错序：终止符 `+`(0x2B) 小于任何数字，所以 `:53.2` 排在 `:53.25` 前、
   `:53+00:00` 排在 `:53.1…` 前——**字典序即时间序**。`AuditTimestampTests` 用三种历史写法混排钉住这条不变量。
   ⚠️ 代价：依赖"偏移恒为 0"，将来要存本地时区必须换成 ticks 列。

**服务与接口**：`QueryAsync` 增 `sort`/`dir`。排序键是**白名单 switch**（`at`/`userName`/`action`/`entityType`/`detail`，
前端传列 prop 名），绝不拼字符串；未知键回退按时间、方向参数保留。每个分支都 `.ThenBy(x => x.Id)`——
按用户名列排序时同值行极多，没有稳定次级键会翻页重复/漏行。`Total` 改 `CountAsync`，页数据 `Skip/Take` 下推。
`AuditController.Query` 加两个 `[FromQuery]`。

**前端**：`tableSort.ts` 加 `SERVER_ORDERS`（只有降/升两态）与 `serverSort(order, prop)`；
审计页 `时间/用户/详情` 三列 `sortable="custom"` + `:default-sort`，`@sort-change` 回第一页再取数。
**动作/实体两列故意不给排序**：它们显示的是中文标签、排的是原始 code，点了会出现"箭头在、顺序看着不对"。

**新增测试**（Execution.Tests）：`AuditTimestampTests` 2 条（ORDER BY/范围比较/分页下推 + 写出格式仍是可比较的那一种）、
`AuditQueryTests` 2 条（12 行翻 4 页不重不漏且时间单调不升；白名单外与注入式排序键回退、负 skip/超大 take 收敛）。

**验证**：`dotnet test RecipesManage.slnx` → Domain 151 / Execution 67 / Contracts 3 全绿，0 警告；`vue-tsc` 通过；
curl 四种 sort 参数返回顺序正确、未知键回退；Playwright 探针实测表头点击发出
`sort=userName&dir=desc→asc`、页面顺序与之一致、翻页不重复、换排序键回到第 1 页，全程 0 个 4xx、0 console 报错（探针已删）。

### 一处值得记住的踩坑
`new DateTimeOffset(y, m, d, h, mi, s, ms, offset)` 的第 7 个参数是**毫秒**：写 `20` 得到的是 `.02` 秒而不是 `.20` 秒，
两次断言都被它坑了。测试时间精度时优先用 `TimeSpan.FromSeconds(...)` 或显式 `.AddMilliseconds`。

## 第十五轮：车道相位真源合一（跳步安全门不再看展示串）

- `BatchLanes.Build` 签名去掉 `handshakePhase` 参数——投影进不来就是编译期保证。
  历史批次重建顺序：该工步最后一条握手事件（且必须是相位令牌）→ 工步结论映射。
