## 易用性改进 第 8 轮：异常与恢复标尺

**标尺**：出了事用户看不看得懂、知不知道该干什么。

### 巡检方法（含一处关键踩坑）

用 playwright 给每页主接口注入 503，检查 error alert 文案 + 重试入口。

**踩坑（重要，务必记住）**：`page.route("**" + api + "*")` 这种通配**极其危险**——`**/api/recipes*` 会同时命中 Vite 的源码模块
`/src/api/recipesTransfer.ts`、`/src/api/equipment.ts?t=...`。结果是：源码模块被 503 掉，真正的 XHR 请求毫发无伤，
页面自然不报错——我据此误判「/recipes 与 /equipment 加载失败无提示」，差点去修一个不存在的 bug。
**正确做法**：用谓词按 pathname 精确匹配，且注意 XHR 走 vite proxy 是**相对路径**（`http://localhost:5173/api/recipes`），
不是 API 直连地址（`localhost:5010`）——
```js
await ctx.route((url) => {
  const p = new URL(url.href).pathname;
  return p === endpoint || p.startsWith(endpoint + "/");
}, (route) => route.fulfill({ status: 503, ... }));
```
另一个细节：`ctx.route` 要在 login **之前**注册（提前于 goto），否则漏网。

### 实测结论（修正后）

8 页**都会**弹红色 alert 讲清原因。出口分布不均：

| 页面 | 报错 | 恢复出口 |
|---|---|---|
| 总览 / 批次 / 设备 | 有 | 4 秒自动轮询重试（自愈，够用） |
| 审计 / 用户 | 有 | 「刷新」按钮 |
| **主配方 / 物料谱系 / 报警** | 有 | **无**——只能刷新整个浏览器 |

## 易用性改进 第 9 轮：键盘可达性标尺

**标尺**：不用鼠标能不能走到、打开每一样东西。

### 巡检方法

写 playwright 脚本逐页统计 `.el-table__body tr` 的 `tabIndex >= 0` 比例（`useKeyboardRows` 会给可点行设 tabindex=0）。

**关键判据：不要只看「可聚焦行数=0」就下结论。** 要分两类：
- 行本身可点（`class="clickable-rows"` + `@row-click`）→ 行必须可聚焦，否则键盘死活打不开。
- 行不可点、操作在列内按钮里（设备页 / 用户页）→ 按钮天然可聚焦，**0 可聚焦行不是缺陷**（设备 52 个按钮、用户 5 个，Tab+Enter 均可达）。

用文本对比法确证：记录右侧面板标题 → 鼠标点第 2 行 → 再 reload 后 `.focus()` 行 + Enter，看编辑器是否切换。行不可聚焦时 `.focus()` 落到 `BODY`。

### 找到并修复的缺口

**`/approval-chains`（审批链配置，Admin 专页）**：左栏链表有 `class="clickable-rows"` + `@row-click="select"`，但**没接 `useKeyboardRows`、也没有 `tableRef`**——键盘用户选不中任何一条链，右侧编辑器永远停在空态。
证据：鼠标点第 2 行 → 编辑器变「编辑 single-review」✅；键盘 `.focus()` 落 `BODY`、Enter 无效 ❌。
修复：加 `ref="tableRef"` + `const tableRef = ref<TableInstance>()` + `useKeyboardRows(tableRef, () => chains.value)`，补 `TableInstance` 类型导入。修复后：focus 落 `TR.el-table__row`，Enter → 「编辑 standard」。

**踩坑（重要）**：该页路由是**顶层 `/approval-chains`**，不是 `/recipes/approval-chains`。后者会被 `recipes/:id` 抢走（静态段优先级高于动态段），实际落到配方详情页并报「配方详情加载失败：接口不存在」——**别被这个报错误导成路由 bug，是探测 URL 写错了**。

- 全站复扫：主配方/批次/物料/报警/审计/审批链 全部 100% 行可聚焦；设备/用户 0 可聚焦属正常（操作在按钮）。
- 临时脚本已删。

## 易用性改进 第 10 轮：表单与对话框人因标尺

**标尺**：填表填到一半，会不会因为一个手滑就全白费。

### 巡检方法

先做静态普查：`grep -rn "before-close\|close-on-click-modal"` 全站对话框 → **0 命中**，说明 9 个含输入的对话框一个保护都没有。再用 playwright 实测三条关闭路径（Esc / 点遮罩 / ×）＋「填一半→关→重开看内容还在不在」。

### 找到的问题

| 表单 | 输入控件 | 填一半后 | 结果 |
|---|---|---|---|
| 设备 / 握手点表 | 24 | Esc | 立即关闭，内容全丢，无提示 |
| 相模板 | 15 | Esc | 同上 |
| 创建批次 | 11 | Esc | 同上 |

**为什么算缺陷而非小瑕疵**：同一份风险，审批链页早就做了确认（`confirmDiscard()`「当前草稿有未保存的修改，继续将丢失这些修改。」），表单却放任 24 字段瞬间蒸发——口径不一致。且 Esc 是用户关下拉/提示的**惯性动作**，误触概率高。

### 改动

新建 `utils/useDialogGuard.ts`：`markClean()` 在铺完表单后记基线，`guardClose(done)` 挂到 `<el-dialog :before-close>`。
- 用 **`before-close`** 而非拦 Esc 按键：这是唯一同时覆盖 Esc/遮罩/× 三条关闭路径的钩子，且自带 done 语义（不调 done 即保持打开）。
- 序列化时把对象键**按字典序排**再比——表单是 `Object.assign` 铺的，键序不稳定，直接 `JSON.stringify` 会误判「有改动」。
- 无改动 or 未 `markClean` 一律放行：空表不打扰，调用方没接管基线时宁放行不误拦。
- 措辞沿用审批链页口径：「表单里有未保存的修改，关闭将丢失这些修改。」/「放弃未保存的修改」。

接入 9 处：`EquipmentFormDialog` / `PhaseTemplateDialog` / `ParallelUnitDialog` / `RecipeHeaderDialog` / `BatchList` / `UserAdmin` / `RecipeList` / `LotList` / `LotGenealogy`（均在「铺完表单」处补 `markClean()`）。

### 验证

- `vue-tsc` 干净；`vitest` 69/69。
- 实测：A 脏表单 Esc → 弹确认、点「取消」对话框在 **且内容保留**（`GUARD-TEST-1` 未丢）；B 点「关闭」→ 真丢弃；C 未改动 Esc → 无确认、直接关。遮罩路径、配方/批次/用户/设备各页均复验。

## 易用性改进 第 12 轮：数据可读性与语义清晰度标尺（i18n 泄漏）

**标尺**：英文界面下，还有没有地方悄悄露出中文。

### 巡檢方法

不用逐页肉眼扫，直接**审扫描器本身**：i18n 覆盖率棘轮的 `KEY_RE` 只能匹配 `t(...)` 调用**内部**的字符串——
`{{ row.drifted ? "是" : "否" }}` 这种字面量压根不在调用里，扫描器**结构上看不见**它。于是棘轮全绿、界面却露中文。
换个说法：棘轮守的是「用了 $t 但没登记译文」，守不住「压根没用 $t」。这就是漏译能活下来的原因。

按这条思路 grep 模板插值里的中文字面量，命中并核实 2 处真泄漏。

### 找到并修复的缺口

| 文件 | 位置 | 原写法 |
|---|---|---|
| `views/batches/BatchMonitor.vue` | log 标签页「漂移」列 | `{{ row.drifted ? "是" : "否" }}` |
| `views/recipes/Approvals.vue` | 审批动作成功提示 | `ElMessage.success(decision === "Approved" ? "已电子签名通过" : "已驳回")` |

- `BatchMonitor` 改成 `$t("是") / $t("否")`。**注意**：批次记录页用的 `components/RecordDriftTable.vue` 同一列写的是 `$t(row.drifted ? "是" : "否")`——是**正确**写法，监控页只是自己内联了一份重复实现、漏了 i18n。修复方向由此得到印证。
- `Approvals` 两个分支加 `t()`；`en.ts` 新增 `"已电子签名通过": "Approved with e-signature"`（`"已驳回": "Rejected"` 已存在）。

### 新增守卫测试（coverage.spec.ts 第 9 条）

`it("模板插值里没有绕过 $t 的裸中文")`：遍历 `.vue` 模板的 `{{ ... }}`，**先把每个 `$t(...)` / `t(...)` / `tipOf(...)` 调用整段抠掉**（按括号配对，能盖住 `$t("编辑 {0}", [draft.code])`、`$t(row.oos ? "超差" : "合格")` 这类带参/嵌套形式；字符串内的括号会跳过），再看剩余文本是否含中文。仍含中文 = 没走 i18n。

**踩坑（务必记住）**：第一版写的是「整段插值表达式是否以 `$t`/`t`/`tipOf` 开头」，结果**误报 12 项**全是合法写法，例如
`row.oos ? $t("超差") : $t("合格")`、`row.equipmentClassCode || $t("未分类")`、`auth.can('Admin') ? $t("编辑") : $t("查看")`、
`tree.lot.quantity == null ? $t("数量未登记") : \`...\`` —— 这些**以非 t 表达式开头**但内部全部已走 `$t`。
判据必须是「抠掉 t 调用后剩没剩中文」，不是「开头是不是 t 调用」。
另需保留豁免：`AppShell.vue` 的语言切换钮 `locale === "en" ? "中文" : "EN"`（英文界面下本就该显示「中文」）。
（另：`components/PageGuideButton.vue` 一度被 grep 疑似大段硬编码中文，实为每个 guide 都有 `"zh-CN"` + `en` 两套，**正确双语**，未改动。）

### 验证

- `vitest run src/i18n/coverage.spec.ts` **9/9** 通过（0 误报）。
- **反向验证**：临时把 `BatchMonitor` 那处改回裸字面量 → 守卫**精确报出仅此一处**；还原后复绿。证明守卫真能抓、不只是空跑。
- `vue-tsc --noEmit` 干净；全量 `vitest run` **70/70**（第 12 轮新增 1 条用例后从 69 → 70）。
- 临时脚本 `frontend/i18n-probe.mjs` 已删。

**结构性结论（值得写进 MEMORY）**：i18n 棘轮（`KEY_RE`）只能扫 `t()` **调用内部**的字符串，**裸字面量是它的结构性盲区**——
裸字面量不在调用里，正则匹配不到。第 12 轮这条新用例是补这个盲区的**唯一**手段，别删。

### 踩坑（两处，都值得记）

1. **`$t(条件 ? "A" : "B")` 是覆盖率棘轮的第二个结构性盲区**。`KEY_RE` 只认「紧跟左括号的字面量」，
